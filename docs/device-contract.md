# Апп · backend · ESP32 өгөгдлийн дүрэм — хувилбар 1

Энэ нь өгөгдлийн төрөл, validation, давхардсан бүртгэлээс хамгаалах нийтлэг дүрэм. Аппын синк болон суурийн endpoint-ууд хэрэгжсэн. Одоогийн холболтын заавар: [3-р ажил — device ingestion](device-ingestion.md), firmware: [firmware/README.md](../firmware/README.md).

Нэг эх сурвалж: `shared/contracts.ts`. Вэб/Capacitor апп нь `src/data.ts`-аар дахин экспортлон ашиглана. Worker мөн энэ модулийг импортлоно. ESP32 C++ код нь доорх JSON хэлбэрийг дагана.

## 1. Уусан / асгасан бүртгэл

```json
{
  "id": "bottle-01-event-0001",
  "amount": 200,
  "type": "drink",
  "at": "2026-10-20T04:00:00.000Z",
  "deviceId": "bottle-01"
}
```

- `id`: тухайн үйлдлийн давтагдахгүй ID. 1–64 үсэг, тоо, зураас. Бүх савны хэмжээнд давхцахгүй байхаар савны ID-г багтаана.
- `deviceId`: төхөөрөмжийн тогтмол ID, мөн 1–64 үсэг, тоо, зураас. Гараар оруулсан хуучин бүртгэлд байхгүй байж болно.
- `amount`: 1–5,000 мл бүхэл тоо; шингэний өөрчлөлт болохоос савны нийт жин биш.
- `type`: `drink` (уусан), `spill` (асгасан), `pending` (тодорхойгүй). Суурь тогтвортой бууралтаас уултыг өөрөө тоолж `POST /api/devices/:id/events`-ээр илгээхэд сервер анх `drink` гэж бүртгэнэ. Сервер хэмжилтээс уулт үүсгэхгүй. Хэрэглэгч дараа `spill` болгон засаж болно.
- `at`: үйл явдал болсон ISO 8601 огноо/цаг. Төхөөрөмж UTC (`Z`) ашиглана; сервер ISO UTC болгон хэвийн болгоно. Интернэт эргэж холбогдсон цагийг эх үйл явдлын цаг болгон сольж болохгүй.

ID ба анхны payload-ийг төхөөрөмж дээр илгээхээс ӨМНӨ хадгална. Дахин асах, retry, холболт тасрахад ижил үйлдэлд шинэ ID эсвэл шинэ timestamp үүсгэхгүй. Дараалсан хоёр ижил хэмжээний уулт нь өөр ID-тай байна. ID нь нэвтрэх түлхүүр биш; төхөөрөмжийн authentication нь тусдаа ажил.

`POST /api/events` нь аппын/хуучин event API. Суурь энэ замыг ашиглахгүй; түлхүүртэй `POST /api/devices/:id/events` нь ижил retry дүрэмтэй. Event API-ийн retry дүрэм:

| Нөхцөл | Хариу |
| --- | --- |
| Шинэ ID | `201`, хадгалсан бүртгэл |
| Өмнөх ID + ижил анхны өгөгдөл | `200`, одоо хадгалагдаж буй бүртгэл; дахин тоолохгүй |
| Өмнөх ID + өөр анхны өгөгдөл | `409`; өмнөх мэдээллийг өөрчлөхгүй |
| Хэрэглэгч устгасан ID + ижил анхны өгөгдөл | `204`; бүртгэлийг сэргээхгүй |
| Төхөөрөмжийн бүртгэл ID-гүй | `400` |
| Буруу хэмжээ, төрөл, огноо, ID | `400` |

Хэрэглэгч `PATCH`-аар төрөл/хэмжээ/огноо зассан ч анхны хүсэлтийн receipt хэвээр байна. Хуучин event хүсэлтийг retry хийхэд хэрэглэгчийн засвар дарагдахгүй. `DELETE` хийсэн ID-г дахин ашиглахгүй; аппын `/api/sync` нь хэрэглэгчийн ил тод undo/backup restore үйлдлээр сэргээж болно. Аппын хадгалалт одоо IndexedDB ашиглана.

Гараар үүсгэх хүсэлтэд хуучин API-ийн адил `id` байхгүй бол сервер UUID үүсгэж болно. Гэхдээ сүлжээний retry хийдэг апп UUID-г өөрөө үүсгэж, ижил хүсэлтэд хэвээр ашиглах ёстой.

## 2. Савны тогтвортой хэмжилт

```json
{
  "version": 1,
  "id": "bottle-01-reading-0042",
  "deviceId": "bottle-01",
  "at": "2026-10-20T04:00:00.000Z",
  "capacityMl": 750,
  "stable": true,
  "remainingMl": 500
}
```

- `capacityMl`: 1–5,000 мл бүхэл тоо.
- `stable: true` үед `remainingMl`: 0–багтаамж хүртэл бүхэл мл. Тогтвортой `0` нь үнэхээр хоосон савыг илэрхийлнэ.
- Сав өргөсөн, хөдөлгөөнтэй, эсвэл хэмжилт боломжгүй үед `stable: false`, `remainingMl: null` илгээнэ. Сав өргөхөд гарсан тэг жинг хоосон сав гэж дамжуулахгүй.
- Савны жин, tare, калибровк, тогтвортой байдлын шийдвэрийг firmware хариуцна. Энэ шатанд код нь хэмжилтийн бодит нарийвчлалыг батлахгүй.
- Дүүргэлт нь уусан бүртгэл биш. `refill`-ийг `/api/events` рүү явуулахгүй; суурь өсөлтийг дүүргэлт гэж үзэж, уусан нийлбэрийг хэвээр үлдээнэ.

`validateDeviceReading()`-ийг төлөвийн endpoint, `validateDeviceEvent()`-ийг уултын endpoint ашиглана. Authentication, timestamp дараалал, baseline/drink/refill болон retry дүрэм: [device-ingestion.md](device-ingestion.md).

## 3. Нийцэл ба шалгах

- `dusal-v1`, `goal`, `mode`, `events` бүтэц хэвээр. Хуучин бүртгэлд `deviceId` шаардахгүй.
- Нөөц хадгалах, сэргээх, бүртгэл засахад байгаа `deviceId`-г алдахгүй.
- D1 migration `0003_event_identity.sql` нь багана, receipt хүснэгт, trigger нэмнэ. Өмнөх бүртгэл, settings устгахгүй. Анхны payload болон устгалын receipt-ийг автоматаар цэвэрлэхгүй.
- Шинэ Worker-ийг асаахаас өмнө migration-ийг тухайн орчинд ажиллуулна. Локал шалгалт `--local`, бодит орчин `--remote` тусдаа. Энэ ажлын хүрээнд remote migration/deploy хийгээгүй.
- Код буцаахад нэмсэн DB багана/хүснэгтийг устгах шаардлагагүй. Trigger нь хуучин Worker-ийн insert/delete үед ч receipt-ийг хадгална; устгасан ID-г дахин ашиглахыг хаана.

```sh
bun run typecheck
bun run test:contract
bun run build
```

Локал Worker-ийн `/api/health` дээр `contractVersion: 1` харагдана. Энэ нь API-ийн кодын хувилбар; бодит төхөөрөмж холбогдсон эсвэл DB migration бэлэн гэдгийг батлахгүй. Аппын синк болон савны төлөв харах UI тусдаа модулиудаар нэмэгдсэн; firmware-ийн бодит суурь дээрх туршилт тусдаа үлдэнэ.
