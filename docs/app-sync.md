# 2-р ажил: апп ↔ backend синк

Бүртгэл нэмэх, засах, устгах, буцаах, нөөцөөс сэргээх болон өдрийн `goal`/`mode` тохиргоог сервертэй синк хийнэ. Нүүр, бүртгэл, түүх, тохиргоо бүгд нэг хадгалалт уншина. Хувийн тооцоолуурын profile, савны гараар тохируулсан үлдэгдэл энэ API-д орохгүй. Бодит төхөөрөмжөөс хэмжилт хүлээн авах нь дараагийн 3-р ажил.

## Хэрэглэх

Анх зөвхөн төхөөрөмжид хадгална. «Сервертэй холбох» тайлбарыг уншиж, холбохоо баталгаажуулсны дараа серверийн бүртгэлтэй нэгтгэнэ. Нэг ID-ийн утга эсвэл өдрийн тохиргоо зөрвөл аль талыг хадгалахаа сонгоно. Хоёр талын өөр өөр шинэ бүртгэлийг хоёуланг хадгална.

- Нэмэх/засах/устгах нь сүлжээ шаардахгүй. Хадгалалт амжилттай болсны дараа UI өөрчлөгдөнө.
- Сүлжээ тасарвал өөрчлөлт IndexedDB-д үлдэнэ. Хуудас дахин нээгдэх, онлайн болох, цонх идэвхжих, 30 секунд тутам эсвэл «Дахин синк хийх» үед оролдоно.
- Апп хаалттай үед сүлжээгээр илгээнэ гэсэн баталгаа байхгүй; дахин нээхэд үргэлжилнэ.
- «Түр зогсоох» нь pending өөрчлөлт, холболтын суурь хувилбарыг устгахгүй. Эхэлсэн серверийн хүсэлт аль хэдийн хүлээн авагдсан байж болно; үргэлжлүүлэхэд ижил ID-гаар баталгаажуулна.
- Хоёр тал нэг бүртгэлийг зассан/устгасан бол сонголт шаардана. Шинэ мэдээлэл ирсэн бол өмнөх сонголтыг дахин баталгаажуулна.
- Шинэ өөрчлөлтийг сүүлчийн серверт баталгаажсан суурьтай харьцуулна. Давтан хүсэлт серверийн шинэ засварыг дарж бичихгүй.

**Одоогийн backend нэвтрэлтгүй, нэг нийтлэг өгөгдлийн сантай. Олон хүний хувийн хэрэглээ, эрүүл мэндийн бодит өгөгдөлд бэлэн биш.** Холбох UI энэ хязгаарыг тайлбарлана. Хэрэглэгчийн auth болон өгөгдлийг эзэмшигчээр тусгаарлахаас өмнө зөвхөн багийн зохиомол өгөгдөл ашиглана.

## Локал ажиллуулах

Production D1-д хүрэхгүй, тусдаа түр хадгалалт ашиглах жишээ:

Терминал 1, repo-ийн `backend/` дотор:

```sh
npm ci
bunx wrangler d1 migrations apply dusal --local --persist-to /private/tmp/dusal-sync-d1
bunx wrangler dev --local --port 8788 --persist-to /private/tmp/dusal-sync-d1
```

Терминал 2, repo-ийн үндсэн folder:

```sh
bun install --frozen-lockfile
VITE_API_URL=http://127.0.0.1:8788 bun run dev --port 5176 --strictPort
```

http://127.0.0.1:5176/entries.html нээнэ. `VITE_API_URL` нь build/dev эхлэхэд авдаг утга. HTTPS сайт болон native build-д HTTPS API ашиглана; HTTP локал хаяг нь компьютер дээрх шалгалтад зориулагдсан. Нэг удаа холбосон серверийн URL локал хадгалалтад тогтмол үлдэнэ; шинэ build өөр сервер рүү өгөгдлийг автоматаар шилжүүлэхгүй.

## Өгөгдлийн хамгаалалт

`src/local-store.ts` нь `dusal-app-v2` IndexedDB-ийн нэг transaction-д snapshot, дарааллын дугаар, синкийн суурь болон дамжуулж буй хүсэлтийг хадгална. Browser storage дүүрвэл transaction бүхэлдээ буцна. `save()` хуудсын уншсан дугаарыг шалгана; өөр цонх/синк өмнө нь өөрчилсөн бол хуучнаар дарж бичихгүй.

Хуучин `localStorage['dusal-v1']`-ийг анхны нээлтээр validate хийж нэг удаа импортлоно. Эх хувийг устгахгүй, шинэ өөрчлөлт IndexedDB-д хадгалагдана. Эвдэрсэн хуучин өгөгдөлтэй бол импорт/хадгалалт зогсоно; баталгаажуулсан нөөц сэргээх үйлдэл л солих эрхтэй. Шинэ хувилбар руу шилжихдээ хуучин табуудыг хааж шинэчилнэ. Хуучин код IndexedDB-ийн шинэ өөрчлөлтийг мэдэхгүй.

Нөөц JSON формат хэвээр. Өгөгдөл browser origin тус бүрд тусдаа: өөр порт, домэйн, native app хооронд local өгөгдөл автоматаар хуулрахгүй. Нөөц татаж хадгалах нь хэвээр хэрэгтэй; browser өгөгдлийг гараар цэвэрлэвэл pending мөн арилна.

Синк IndexedDB lease-аар нэг browser-ийн табуудын хооронд дарааллана. Network POST-оос өмнө хүсэлт тогтмол ID-тайгаар хадгалагдана. Сервер хүлээн аваад хариу замдаа тасарсан ч дахин нээхэд ижил хүсэлтийг давтаж, давхар бүртгэл үүсгэхгүй. Илгээх зуур хийсэн шинэ өөрчлөлтийг ACK дарж бичихгүй.

## Серверийн дүрэм

`0004_app_sync.sql` нь өгөгдөл устгахгүй нэмэлт migration. Worker-ийг гаргахаас өмнө 0001–0004 migration шаардлагатай. **Энэ өөрчлөлтийг локал шалгасан; remote migration/deploy хийгээгүй.**

- `GET /api/sync` → `{ revision, state: { goal, mode, events } }`. Нэг D1 batch-аар нийцтэй snapshot авна. Response `Cache-Control: no-store`.
- `POST /api/sync` → `{ id, baseRevision, state }`; амжилттай `{ id, revision }`.
- `409 { code: "revision" }` → суурь хуучирсан, ямар ч өөрчлөлт хийхгүй; шинэ snapshot-тай нэгтгээд шинэ ID-тай хүсэлт үүсгэнэ.
- Ижил ID + ижил анхны payload → нэг удаа хэрэглэнэ, ижил ACK буцаана. Ижил ID + өөр payload → `409 { code: "id_reused" }`.
- Бүх update/delete/undo, тохиргоо, revision, receipt нэг D1 transaction. Аль нэг statement унавал бүхэлдээ буцна.
- Хуучин `/api/events`, `/api/settings` замууд болон шууд SQL event өөрчлөлтүүд trigger-ээр revision нэмнэ. Хэмжилтийн ingestion нэмэхдээ энэ дүрмийг хадгална.
- Аппын ил тод undo/backup restore нь устгасан ID-г сэргээж болно. `/api/events`-ийн төхөөрөмжийн retry устгасан бүртгэлийг сэргээхгүй.

`shortcut: Бүтэн snapshot POST нь 5 MB хүртэл; өгөгдөл энэ хэмжээнд дөхөхөд incremental өөрчлөлтийн API руу шилжинэ.` Татсан snapshot-ын хязгаарыг зориуд тайрч болохгүй: тайрсан жагсаалтыг бүтэн төлөв гэж үзвэл хуучин түүхийг устгах эрсдэлтэй.

## Шалгах

```sh
bun run test:contract
bun run test:sync
bun run build
node --check public/sw.js
```

Тестүүд Worker-ийн жинхэнэ SQL-ийг in-memory SQLite дээр, IndexedDB transaction-уудыг `fake-indexeddb` дээр ажиллуулна. Offline/restart, алдагдсан ACK, давтан хүсэлт, илгээх зуурын засвар, давхар writer, conflict сонголт, delete/undo, хуучин өгөгдөл импорт, validation rollback, stale save, pause/resume нөхцөлүүдийг шалгана. Бодит утас, load cell болон production өгөгдөл дээрх баталгаажуулалт тусдаа үлдэнэ.

## Буцаах

Нэвтрүүлэхийн өмнө JSON нөөц болон D1 нөөц авна. Аппыг хуучин bundle рүү буцаахаас өмнө шинэ аппын JSON нөөцийг татна: хуучин bundle зөвхөн анхны `dusal-v1` snapshot-ыг унших тул шинэ IndexedDB өөрчлөлтийг харахгүй. Хуучин хувилбарт JSON-оор сэргээх шаардлагатай. Нэмэлт D1 migration-ийг буцааж устгахгүй; хуучин endpoint-ууд хэвээр ажиллана. Шинэ client-д шаардлагатай `/api/sync`-гүй Worker рүү буцаавал pending төхөөрөмжид үлдэж, синк алдаа харуулна.
