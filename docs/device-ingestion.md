# 3-р ажил: ухаалаг суурь → backend → апп

Хүн дурын саваа суурин дээр тавина. Суурь (load cell + HX711 + ESP32-S3) жингийн өөрчлөлтөөс **уусан хэмжээг өөрөө тооцож**, Wi-Fi/HTTPS-ээр серверт илгээнэ. Апп `/api/sync`-ээр бүртгэлээ авч, `/api/devices`-ээс суурийн төлөвийг (үлдэгдэл, өргөсөн эсэх, сүүлд хэзээ мэдээлсэн) харуулна. Firmware: [firmware/README.md](../firmware/README.md).

Уусныг **зөвхөн суурь** тоолно. Сервер хэмжилтээс уулт үүсгэхгүй, тиймээс нэг уулт хоёр удаа тоологдохгүй.

## 1. Уусан хэмжээ — `POST /api/devices/:id/events`

```http
Content-Type: application/json
Authorization: Bearer <тухайн суурийн нууц түлхүүр>
```

```json
{ "version": 1, "id": "base-01-e-5-12", "deviceId": "base-01", "at": "2026-10-20T10:00:00.123Z", "amount": 250 }
```

- Сервер үүнийг `type: "drink"`, `deviceId`-тай бүртгэл болгоно. Суурь асгасан эсэхийг мэдэхгүй тул `type` илгээхгүй; хэрэглэгч апп дээр «Асгасан» болгоно.
- `id` нь суурь дээр уултыг бүртгэх үед тогтдог (`<deviceId>-e-<асалтын дугаар>-<уултын дугаар>`), flash-д хадгалагдана. Retry, дахин асах үед солигдохгүй.

| Хариу | Утга | Суурь юу хийх |
|---|---|---|
| `201` | Шинэ уулт хадгалагдлаа | Дараалаас хасна |
| `200` | Ижил уултыг аль хэдийн хүлээн авсан (retry) | Дараалаас хасна |
| `204` | Хэрэглэгч энэ уултыг устгасан; дахин үүсгэхгүй | Дараалаас хасна |
| `409` | Ижил ID өөр хэмжээтэй | Хасаж, тоолно (засагдахгүй алдаа) |
| `400` / `413` | Буруу өгөгдөл / хэт том | Хасаж, тоолно |
| `401` | ID эсвэл түлхүүр буруу | Хадгалж, дараа дахин оролдоно |
| `503`, `5xx`, сүлжээ | Түр алдаа | Хадгалж, 5 сек → 5 мин хүртэл уртасгаж дахин оролдоно |

Retry нь хэрэглэгчийн «Асгасан» засварыг дарж бичихгүй, устгасныг сэргээхгүй. Серверээс 5 минутаас илүү ирээдүйн цагийг хүлээж авахгүй.

## 2. Төлөв — `POST /api/devices/:id/readings`

```json
{ "version": 1, "id": "base-01-r-5-3", "deviceId": "base-01", "at": "2026-10-20T10:00:00.123Z", "capacityMl": 750, "stable": true, "remainingMl": 500 }
```

- Зөвхөн аппад харуулах төлөв. **Уулт үүсгэхгүй**, бүртгэл болон синкийн revision-д нөлөөлөхгүй.
- Үлдэгдэл мэдэгдэхгүй үед (сав өргөсөн, хөдөлж байгаа, хоосон савны жинг тохируулаагүй) `stable: false, remainingMl: null`. Апп `?` харуулна, хоосон гэж харуулахгүй.
- `capacityMl` нь хүн дурын савны хувьд таамаг: хоосон савны жинг тохируулснаас хойш харсан хамгийн их усны хэмжээ (тодорхойгүй бол 1).
- 15 секунд тутам болон үлдэгдэл өөрчлөгдсөн даруйд илгээнэ; дараалалд хадгалахгүй (хамгийн сүүлийнх л хэрэгтэй). Хуучин эсвэл ижил цагтай хэмжилт `outcome: "stale"` болж, одоогийн төлөвийг өөрчлөхгүй.

## Суурийн тооцоолох дүрэм

Firmware-ийн `lib/dusal_core/intake` нь `shared/device.ts`-ийн босготой ижил.

| Нөхцөл | Үйлдэл |
|---|---|
| Жин 1.5 сек 15 г-ийн дотор тогтвортой | Тогтворжсон гэж үзээд 200 мс зайтай 4 хэмжилт авч, дундажийг нь өмнөх тогтвортой жинтэй харьцуулна |
| Анх сав тавигдсан | Эхлэлийн цэг; уулт биш |
| Суурь хоосон (сав өргөсөн) | Эхлэлийн цэгийг хадгална; хэзээ ч «бүгдийг уусан» гэж тооцохгүй |
| ≥100 г буурсан | Зөрүүгээр нэг уулт (автоматаар «уусан» гэж бүртгэнэ) |
| ≥20 г нэмэгдсэн | Дүүргэлт; уусан нийлбэр хэвээр |
| 100 г-аас бага буурсан, 20 г-аас бага нэмэгдсэн | Уулт биш; эхлэлийн цэг хэвээр тул жижиг балгалтууд хуримтлагдаж, нийлээд 100 г хүрмэгц нэг уулт болно |
| 5000 г-аас их үсрэлт | Өөр сав; уулт биш, хоосон савны жинг арилгана |

Хязгаар: хүнд савыг аваад хөнгөн аяга тавивал суурь «уусан» гэж андуурна; хэрэглэгч апп дээр бүртгэлийг засна/устгана эсвэл шинэ савандаа BOOT товч дарна. `100 г`, `20 г`, `15 г`, `1.5 сек` нь прототипийн утга; бодит load cell дээр туршиж тохируулна.

## Төхөөрөмжийн түлхүүр

`DEVICE_TOKENS` Worker secret нь ID → нууц түлхүүр гэсэн JSON объект байна. Төхөөрөмж бүр **өөр**, дор хаяж 32 тэмдэгттэй санамсаргүй түлхүүртэй; `openssl rand -hex 32`-оор үүсгэж болно. ID өөрөө нууц биш. Түлхүүрийг frontend, Git, issue/PR, screenshot, firmware-ийн нийтэд харагдах эх кодод оруулахгүй.

Локал `backend/.dev.vars` файлд single quote дотор JSON бичнэ:

```dotenv
DEVICE_TOKENS='{"bottle-01":"<энд өөрийн 64 hex санамсаргүй түлхүүр>"}'
```

Дээрх `<...>` нь placeholder, ажиллах түлхүүр биш. `.dev.vars` Git-д ignored. Файлыг өөрчилсний дараа Wrangler dev-ийг дахин асаана. Production-д зөвшөөрөлтэй нэвтрүүлэх үед `wrangler secret put DEVICE_TOKENS` ашиглан JSON-оо интерактив оруулна; энэ ажлаар secret upload/deploy хийгээгүй. Түлхүүр солиход ижил ID-тай firmware-ийг мөн шинэчилнэ; сервер хуучин түлхүүрийг шууд хүлээж авахаа болино.

Энэ нь суурийн хоёр endpoint-ийг (`/events`, `/readings`) хамгаална. Өмнөх аппын CRUD/sync/status endpoint-ууд нэвтрэлтгүй, нэг нийтлэг өгөгдлийн сантай хэвээр. Олон хэрэглэгчийн хувийн хэрэглээнд гаргахаас өмнө auth болон өгөгдлийн эзэмшлийг тусгаарлах шаардлагатай. Төхөөрөмжийн түлхүүрийг апп руу дамжуулах шаардлагагүй.

## Апп дээр

1. Сервертэй синк хийхээ баталгаажуулна.
2. Нүүрийн «Миний сав» хэсгээс суурийн ID-г сонгоно.
3. Савны багтаамж/үлдэгдэл хэмжилтээс ирнэ. Хэмжилтийн горимд «Дүүргэсэн», багтаамжийн гараар тохируулах товч харагдахгүй.
4. Хэмжилт/хүлээн авсан цагийн аль нэг нь 60 секундээс хуучирвал эсвэл серверт холбогдохгүй бол “сүүлчийн хэмжилт” гэж харуулна. Найдваргүй үед `?` харуулна. Онлайн heartbeat нь жингийн заалт тогтвортой гэсэн үг биш.
5. Суурийн тоолсон уулт синкээр бүртгэлд орно. Доорх гараар нэмэх товчийг зөвхөн өөр аяга, савнаас уусан усанд ашиглана.

Савны сонголт болон сүүлчийн баталгаажсан хэмжилт IndexedDB-д хадгалагдана. Offline үед сүүлчийн утга харагдана, холбогдсон гэж таахгүй. Хэмжилт шинэчлэх нь бичиж буй өдрийн тохиргооны form-ийг дахин бүтээхгүй. Синк paused үед device polling мөн зогсоно.

## Локал ажиллуулах ба баталгаажуулах

Өмнөх 0001–0004 дээр нэмээд `0005_device_readings.sql` шаардлагатай. Migration нь хуучин бүртгэл/тохиргоо/receipt/revision-ийг өөрчлөхгүй. Тусдаа локал сан:

```sh
# backend/ дотор; .dev.vars-д локал түлхүүрээ тохируулсны дараа
bunx wrangler d1 migrations apply dusal --local --persist-to /private/tmp/dusal-device-d1
bunx wrangler dev --local --port 8790 --persist-to /private/tmp/dusal-device-d1

# repo root, өөр терминал
VITE_API_URL=http://127.0.0.1:8790 bun run dev --port 5177 --strictPort
```

`http://127.0.0.1:5177/` нь энэ компьютерийн локал preview. ESP32-д `127.0.0.1` нь өөрийнх нь хаяг учраас firmware дээр ийм хаяг ашиглахгүй. Бодит холболтод HTTPS API URL, Wi-Fi, зөв UTC цаг, тухайн төхөөрөмжийн түлхүүр хэрэгтэй. Төхөөрөмж бэлэн болсны дараа бодит calibration/өргөлт/угаалт/цэнэгийн туршилт хийнэ.

```sh
bun run test:contract
bun run test:sync
bun run test:device
bun run test:firmware
bun run build
node --check public/sw.js
```

Тестүүд бодит Worker SQL-ийг SQLite дээр ажиллуулж, auth, суурийн уултын retry/засвар/устгал, төлөвийн stale/out-of-order, concurrent retry, rollback-ийг шалгана. Суурийн төлөв + уулт → app sync → cached status бүрэн урсгал мөн тесттэй. `bun run test:firmware` нь firmware-ийн тооцоолол, дараалал, JSON-ийг компьютер дээр шалгаж, тэр JSON-ийг жинхэнэ Worker-т илгээж шалгана. Локал Wrangler/D1 дээр synthetic payload-оор шалгасан нь бодит load cell-ийн нарийвчлал, утасны app/HTTPS deployment шалгагдсан гэсэн үг биш.

## Буцаах

Хуучин Worker рүү буцаахад нэмсэн device хүснэгтүүдийг устгахгүй. `/events`-гүй Worker 404 буцаах тул суурь уултаа дараалалд хадгалсаар (404 нь түр алдаа гэж үзэгдэнэ), шинэ Worker буцаж ирэхэд илгээнэ. `/api/devices`-гүй сервертэй үед шинэ апп cached хэмжилт + холболтын алдаа харуулна; гараар бүртгэх болон өмнөх sync хэвээр ажиллана. Хуучин апп `bottles` нэмэлт metadata-г хадгалсаар байх ба үндсэн events/settings формат хэвээр. Хэмжилтийн receipt-үүдийг цэвэрлэхгүй: өмнөх ID-гийн replay хамгаалалт тэдгээрээс хамаарна.
