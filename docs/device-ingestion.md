# 3-р ажил: load cell → backend → апп

Савны ёроолын load cell + HX711-ийн шүүсэн хэмжилтийг ESP32-S3 Wi-Fi/HTTPS-ээр серверт илгээнэ. Сервер хэмжилтээс уусан/нэмсэн өөрчлөлтийг ялгана. Апп өмнөх `/api/sync`-ээр бүртгэлээ авч, `/api/devices`-ээс савны бодит үлдэгдлийг харуулна. Firmware, утсанд Wi-Fi тохируулах, Bluetooth pairing энэ ажлын хүрээнд ороогүй.

## Хэмжилт илгээх

`POST /api/devices/bottle-01/readings`

```http
Content-Type: application/json
Authorization: Bearer <тухайн савны нууц түлхүүр>
```

```json
{
  "version": 1,
  "id": "bottle-01-reading-00042",
  "deviceId": "bottle-01",
  "at": "2026-10-20T10:00:00.000Z",
  "capacityMl": 750,
  "stable": true,
  "remainingMl": 500
}
```

Тогтвортой бус үед `stable: false`, `remainingMl: null`. Өргөсөн савны тэг жинг `stable: true, remainingMl: 0` болгон илгээж болохгүй. Firmware энэ ялгааг load cell-ийн механик суурилуулалт, tare, тогтвортой байдлын шалгалтаар батлах ёстой; backend JSON-оос дангаар нь физик өргөлтийг таних боломжгүй.

Амжилттай хариу:

```json
{
  "id": "bottle-01-reading-00042",
  "deviceId": "bottle-01",
  "outcome": "drink",
  "eventId": "dev-<60 hex тэмдэгт>"
}
```

- Хэмжилт бүр өөр, төхөөрөмж дээр урьдчилан хадгалсан ID-тай байна. Нэг төхөөрөмж дотор `at` өсөх дараалалтай, миллисекундээр ялгаатай UTC байна. Төхөөрөмж эхлээд цагийг NTP-ээр тохируулна.
- Pending хэмжилтүүдийг **хуучнаас нь нэг нэгээр** илгээнэ. 200 ACK авсны дараа л тухайн pending-ийг арилгана. Сүлжээ тасарвал ID, timestamp, payload-ийг солихгүй.
- Firmware зөвхөн энэ endpoint рүү хэмжилт явуулна. Ижил бууралтад нэмээд `/api/events` рүү drink явуулбал давхар тоолох тул явуулахгүй. Drink-ийг сервер үүсгэнэ.
- 401 → ID/түлхүүрээ шалгах; 400 → payload/UTC цагийг засах; 409 → ижил ID-г өөр payload-д дахин хэрэглэсэн; 413 → body 4096 byte-аас их; 503/network error → ижил хүсэлтийг дараа дахин илгээх. Түлхүүр тохируулаагүй сервер 503 буцаана.
- Серверээс 5 минутаас илүү ирээдүйн огноог хүлээж авахгүй. Хуучин offline багцыг зөв дарааллаар илгээж болно. Хожим ирсэн хуучин/ижил timestamp-тай шинэ ID-г `outcome: stale` гэж ACK хийгээд одоогийн үлдэгдэл, түүхийг өөрчлөхгүй.
- Сүлжээтэй үед 15 секунд орчим тутам, төлөв өөрчлөгдөхөд мөн хэмжилт илгээнэ. Retry нь шинэ heartbeat биш; хуучин ID-г дахин илгээх нь online төлөвийг сунгахгүй.

## Тооцоолох дүрэм

`shared/device.ts` нь нийтлэг дүрэм. Хэмжилтийн бодит нарийвчлалын баталгаа биш.

| Нөхцөл | Үйлдэл |
|---|---|
| Анхны тогтвортой хэмжилт | Суурь тогтооно, уусан гэж тооцохгүй |
| Найдваргүй/өргөсөн (`false/null`) | Үлдэгдэл `?`; өмнөх найдвартай суурийг хадгална, уусан гэж тооцохгүй |
| Сууриас 10 мл-ээс бага зөрүү | Noise гэж үзнэ; жижиг бууралтууд сууриасаа хуримтлагдана |
| Сууриас ≥10 мл буурсан | Зөрүүгээр нэг `drink` бүртгэл үүсгэнэ; тогтвортой 0 хүртэл бууралтыг мөн тооцно |
| Сууриас ≥10 мл нэмэгдсэн | Refill; үлдэгдэл/суурийг шинэчилнэ, өмнөх уусан хэмжээ хэвээр |
| Багтаамж өөрчлөгдсөн | Шинэ суурь; drink үүсгэхгүй |
| Сүүлчийн тогтвортой хэмжилтээс >5 минут тасарсан | Resync; хооронд болсон зүйлийг таахгүй, шинэ үлдэгдлийг суурь болгоно |

`MIN_CHANGE_ML = 10` нь прототипийн шүүлтүүрийн босго. Бодит load cell-ийн туршилтаар noise-ийг хэмжиж байж тохируулна; ±10 мл нарийвчлал гэсэн үг биш. Тасалдсан хоорондын хэрэглээг алдаагүй сэргээх баталгаа байхгүй: уух, дүүргэх, асгах аль нь болсныг хоёрхон заалтаас ялгах боломжгүй. Resync-ийн дараа шаардлагатай хэрэглээг гараар бүртгэнэ.

Анхны default нь drink; хэрэглэгч асгасан бол spill болгон өөрчилнө. Засвар/устгал нь firmware-ийн жингийн суурийг өөрчлөхгүй. Ижил хэмжилтийн retry нь хэрэглэгчийн засварыг дарж бичихгүй, устгасан бүртгэлийг сэргээхгүй.

## Төхөөрөмжийн түлхүүр

`DEVICE_TOKENS` Worker secret нь ID → нууц түлхүүр гэсэн JSON объект байна. Төхөөрөмж бүр **өөр**, дор хаяж 32 тэмдэгттэй санамсаргүй түлхүүртэй; `openssl rand -hex 32`-оор үүсгэж болно. ID өөрөө нууц биш. Түлхүүрийг frontend, Git, issue/PR, screenshot, firmware-ийн нийтэд харагдах эх кодод оруулахгүй.

Локал `backend/.dev.vars` файлд single quote дотор JSON бичнэ:

```dotenv
DEVICE_TOKENS='{"bottle-01":"<энд өөрийн 64 hex санамсаргүй түлхүүр>"}'
```

Дээрх `<...>` нь placeholder, ажиллах түлхүүр биш. `.dev.vars` Git-д ignored. Файлыг өөрчилсний дараа Wrangler dev-ийг дахин асаана. Production-д зөвшөөрөлтэй нэвтрүүлэх үед `wrangler secret put DEVICE_TOKENS` ашиглан JSON-оо интерактив оруулна; энэ ажлаар secret upload/deploy хийгээгүй. Түлхүүр солиход ижил ID-тай firmware-ийг мөн шинэчилнэ; сервер хуучин түлхүүрийг шууд хүлээж авахаа болино.

Энэ нь **төхөөрөмжийн хэмжилтийн endpoint**-ийг хамгаална. Өмнөх аппын CRUD/sync/status endpoint-ууд нэвтрэлтгүй, нэг нийтлэг өгөгдлийн сантай хэвээр. Олон хэрэглэгчийн хувийн хэрэглээнд гаргахаас өмнө auth болон өгөгдлийн эзэмшлийг тусгаарлах шаардлагатай. Төхөөрөмжийн түлхүүрийг апп руу дамжуулах шаардлагагүй.

## Апп дээр

1. Сервертэй синк хийхээ баталгаажуулна.
2. Нүүрийн «Миний сав» хэсгээс анхны хэмжилтээ илгээсэн савны ID-г сонгоно.
3. Савны багтаамж/үлдэгдэл хэмжилтээс ирнэ. Хэмжилтийн горимд «Дүүргэсэн», багтаамжийн гараар тохируулах товч харагдахгүй.
4. Хэмжилт/хүлээн авсан цагийн аль нэг нь 60 секундээс хуучирвал эсвэл серверт холбогдохгүй бол “сүүлчийн хэмжилт” гэж харуулна. Найдваргүй үед `?` харуулна. Онлайн heartbeat нь жингийн заалт тогтвортой гэсэн үг биш.
5. Доорх гараар нэмэх товчийг өөр аяга, савнаас уусан усанд ашиглана; сонгосон савны уултыг дахин гараар нэмэхгүй.

Савны сонголт болон сүүлчийн баталгаажсан хэмжилт IndexedDB-д хадгалагдана. Offline үед сүүлчийн утга харагдана, холбогдсон гэж таахгүй. Хэмжилт шинэчлэх нь бичиж буй өдрийн тохиргооны form-ийг дахин бүтээхгүй. Синк paused үед device polling мөн зогсоно.

## Локал ажиллуулах ба баталгаажуулах

Өмнөх 0001–0004 дээр нэмээд `0005_device_readings.sql` шаардлагатай. Migration нь хуучин бүртгэл/тохиргоо/receipt/revision-ийг өөрчлөхгүй. Тусдаа локал сан:

```sh
# backend/ дотор; .dev.vars-д локал түлхүүрээ тохируулсны дараа
bunx wrangler d1 migrations apply dusal --local --persist-to /private/tmp/dusal-device-d1
bunx wrangler dev --local --port 8790 --persist-to /private/tmp/dusal-device-d1

# repo root, өөр терминал
VITE_API_URL=http://127.0.0.1:8790 bun run dev --port 5177 --strictPort
```

`http://127.0.0.1:5177/` нь энэ компьютерийн локал preview. ESP32-д `127.0.0.1` нь өөрийнх нь хаяг учраас firmware дээр ийм хаяг ашиглахгүй. Бодит холболтод HTTPS API URL, Wi-Fi, зөв UTC цаг, тухайн төхөөрөмжийн түлхүүр хэрэгтэй. Төхөөрөмж бэлэн болсны дараа бодит calibration/өргөлт/угаалт/цэнэгийн туршилт хийнэ.

```sh
bun run test:contract
bun run test:sync
bun run test:device
bun run build
node --check public/sw.js
```

Тестүүд бодит Worker SQL-ийг SQLite дээр ажиллуулж, auth, baseline/drink/refill/empty/unstable/noise, stale/out-of-order, concurrent retry, rollback болон хэрэглэгчийн засвар/устгалыг шалгана. Ingestion → app sync → cached device status гэсэн бүрэн урсгал мөн тесттэй. Локал Wrangler/D1 дээр synthetic payload-оор шалгасан нь бодит load cell-ийн нарийвчлал, утасны app/HTTPS deployment шалгагдсан гэсэн үг биш.

## Буцаах

Хуучин Worker рүү буцаахад нэмсэн device хүснэгтүүдийг устгахгүй. `/api/devices`-гүй сервертэй үед шинэ апп cached хэмжилт + холболтын алдаа харуулна; гараар бүртгэх болон өмнөх sync хэвээр ажиллана. Хуучин апп `bottles` нэмэлт metadata-г хадгалсаар байх ба үндсэн events/settings формат хэвээр. Хэмжилтийн receipt-үүдийг цэвэрлэхгүй: өмнөх ID-гийн replay хамгаалалт тэдгээрээс хамаарна.
